# 2026-09-13 — Android FCM server delivery

## Scope

SautiLink Android push delivery now extends the existing notification permission + device-token foundation without replacing Supabase Auth/database or Cloudflare R2.

## Architecture

- Firebase Cloud Messaging handles Android push transport.
- `public.push_device_tokens` remains the authenticated user ↔ Android installation/token registry.
- `public.push_delivery_queue` is server-owned and inaccessible to anon/authenticated clients.
- Inserts into `social_notifications` queue follow, like, reply, mention, and repost pushes.
- Inserts into `dm_messages` queue message pushes for the other conversation participant.
- PostgreSQL `pg_net` dispatches queue items asynchronously to the `sautilink-push-dispatch` Supabase Edge Function.
- `pg_cron` retries transient failures up to five attempts.
- The Edge Function reads `FIREBASE_SERVICE_ACCOUNT_JSON_BASE64` from Supabase secrets and uses FCM HTTP v1.
- Invalid/unregistered FCM tokens are removed automatically.

## Privacy and routing

Direct-message push text is intentionally generic and does not expose message contents on the lock screen. Push taps use the existing safe routes: profile, post, notifications, or a specific message conversation.

## Security

Firebase private credentials are not committed to GitHub. The Edge Function accepts only an unguessable queue ID + dispatch key pair generated by PostgreSQL; queue rows are not readable by clients.

## Validation

- Edge Function deployed successfully to production Supabase.
- Queue migration applied successfully.
- `pg_net`, `pg_cron`, social-notification trigger, DM trigger, and retry cron job verified present.
- A synthetic invalid dispatch returned `404 dispatch_not_found`, confirming the function endpoint, Supabase secret decoding, and queue-key validation are active without sending a real notification.
